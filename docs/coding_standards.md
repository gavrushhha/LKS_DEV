# Стандарты оформления кода и разработки LKS_DEV

Единый стандарт для команды (backend, frontend, Git). Зафиксирован на базе анализа веток `main`, `T2/source_layer`, `T5` и `alena-backend-foundation`.

---

## 1. Общие правила и язык

* **На русском языке**: комментарии в коде, докстринги, тексты ошибок для пользователя (`title`, `detail`), описания в OpenAPI (`summary`, `description`), пользовательский интерфейс и проектная документация (`docs/`, `README.md`).
* **На английском языке**: идентификаторы в коде, имена таблиц/колонок/схем, машиночитаемые коды ошибок (`code`), имена событий и ключи в логах (`event`, `title`, `key=value`).
* Качество кода проверяется автоматически (`ruff`, `mypy --strict`, `pytest`, pre-commit и CI).

---

## 2. Именование

### Backend (Python)

* Переменные, функции, методы, аргументы, модули и пакеты — **`snake_case`** (`date_from`, `get_schedule`, `snapshot_sync.py`).
* Классы, Pydantic-схемы, исключения, `TypeAlias` — **`PascalCase`** (`ScheduleService`, `ApiError`).
* Константы уровня модуля — **`UPPER_SNAKE_CASE`** (`PROBLEM_CONTENT_TYPE`, `_LIMIT`).
* Внутренние хелперы модуля и приватные атрибуты — с ведущим подчёркиванием (`_open_pool`, `self._repository`).
* Поля API-схем (JSON / OpenAPI) — **`snake_case`** (`pair_number`, `trace_id`, `pass_value`).
  * Исключение: внешние интеграционные конверты, чья спецификация жёстко требует другой формат (например, `routingHeader`, `operationType` в адаптере НСИ).

### Frontend (Этап 2: React / Vue + TypeScript)

* Переменные, функции, методы, пропсы, хуки/composables — **`camelCase`** (`dateFrom`, `useSchedule`).
* Компоненты, интерфейсы, типы, классы — **`PascalCase`** (`ScheduleTable`, `GradeItem`).
* Константы — **`UPPER_SNAKE_CASE`**.
* Преобразование полей API (`snake_case` ↔ `camelCase`) выполняется централизованно на уровне API-клиента/адаптера, чтобы не смешивать стили внутри UI-компонентов.

## 3. Докстринги и комментарии

### Backend

* Короткий однострочный русский докстринг **обязателен**:
  1. В начале **каждого `.py`-файла** (кроме пустых `__init__.py` без кода).
  2. У **каждого публичного класса**.
  3. У **каждой публичной функции и метода** (роутеры, сервисы, репозитории, клиенты, зависимости).
* Для приватных хелперов докстринг добавляется, если название не исчерпывает поведение.
* Комментарии в коде пишутся на русском и объясняют **почему** принято решение, а не пересказывают синтаксис.
* Формат отложенных задач: `# TODO(T3.3): краткое описание`.

#### Форма докстрингов (принятый стандарт)

* **Модули и классы** — назывная форма (1 строка, точка на конце):
  * Модуль: `"""Слой чтения расписания из источника и кэша."""`
  * Класс: `"""Пул соединений с репликой БД Тандема."""`
* **Функции и методы** — инфинитив (1 строка, точка на конце):
  * Функция/метод: `"""Получить актуальное расписание за указанный период."""`
* Не использовать форму 3-го лица (`"""Возвращает..."""`), чтобы не смешивать стили между файлами.

### Frontend

* Публичные компоненты, хуки, утилиты и функции API-клиента документируются коротким JSDoc/TSDoc на русском:
  ```ts
  /** Загрузить расписание учебной группы за выбранный период. */
  export async function fetchGroupSchedule(groupId: string, dateFrom: string): Promise<ScheduleList> { ... }
  ```

## 4. Логирование (`structlog`)

### Базовая настройка

* Инициализация выполняется один раз в `lifespan` через `configure_logging(settings.log_level)`.
* Для каждого HTTP-запроса `request_id_middleware` выставляет `trace_id` (из `X-Request-ID` или `uuid4()`) и привязывает его через `structlog.contextvars.bind_contextvars(trace_id=request_id)`.

### Формат событий

* Первый аргумент (`event`) — короткое событие на английском в `snake_case`.
* Если добавляется `title` (для наглядности в агрегаторе логов) — на английском.
* Все поля контекста — в `snake_case` на английском; никаких f-строк в имени события.

```python
# Правильно
logger.info(
    "schedule_snapshot_synced",
    title="Schedule snapshot synced",
    scope=scope,
    entries_count=len(entries),
)

# Правильно (ожидаемая деградация с fallback)
logger.warning(
    "dictionary_cache_read_failed",
    title="Dictionary cache read failed",
    dictionary=kind,
    error_type=type(exc).__name__,
)

# Неправильно: f-строка в событии, русские ключи, утечка DSN/ПДн
logger.info(f"Не удалось прочитать кэш для {dsn}: {exc}")
```

### Где логи обязательны

* `INFO`: старт и остановка приложения (`app_started`, `app_stopped`), старт и завершение фоновых/периодических операций (синхронизация снимков, обработка очередей).
* `WARNING`: **деградация и восстанавливаемые сбои** — падение Redis с переходом на источник, переход на локальный снимок расписания (`stale`), недоступность зависимости в `/ready`, превышение бюджета запросов к Тандему.
* `ERROR` / `EXCEPTION`: необработанные 5xx-ошибки (`logger.exception("unhandled_exception")`), критические отказы интеграций, прерывающие выполнение операции.

### Политика при деградации

* При **ожидаемой деградации с работающим fallback** (кэш недоступен → идём в БД; проверка `/ready` не прошла) пишем `logger.warning(..., error_type=type(exc).__name__)` без стектрейса, чтобы не зашумлять stdout при серии запросов.
* При **неожиданном сбое / 5xx** пишем `logger.exception(...)` с полным стектрейсом для диагностики.

### Что запрещено логировать

* Пароли, секреты, API-ключи, полные DSN с учётными данными (`lks_db_dsn`, `tandem_db_dsn`, `redis_dsn`, `rabbitmq_dsn`).
* JWT-токены, содержимое заголовков `Authorization`, `Cookie`.
* Персональные данные (ФИО, email, телефоны, данные паспортов, оценки конкретных студентов) и полные тела HTTP-запросов/ответов.

### Frontend

* В коде, попадающем в ветку, запрещены отладочные `console.log` / `console.debug`.
* Ошибки клиента отправляются только через централизованный обработчик без токенов и ПДн.

## 5. Архитектура, зависимости и конфигурация (Backend)

* Разделение слоёв: `api/v1` (HTTP, схемы, права) → `services` (бизнес-логика, кэширование) → `repositories` / `source` (БД ЛКС, Тандем, внешние сервисы).
* **Жизненный цикл и DI — строго через `lifespan` + `app.state` + `Depends`**:
  * Все пулы и общие клиенты (`db`, `redis`, `tandem`, `rabbitmq`) инициализируются один раз в `lifespan` (`app/main.py`) и корректно закрываются в блоке `finally`.
  * Роутеры и сервисы получают зависимости только через `Annotated[..., Depends(...)]` из `app/core/deps.py` (или профильных модулей `deps`).
  * **Запрещено** создавать `create_async_engine` в отдельных модулях вне `lifespan`, открывать/закрывать клиент `Redis` на каждый запрос и инстанцировать `Repository()`/`Service()` вручную внутри HTTP-эндпоинта.
* Все секреты и DSN в `Settings` (`app/core/config.py`) описываются типом `SecretStr`.
* Слой `app/source/tandem/` работает **только на чтение (`SELECT`)**; запрет записи контролируется автотестом `tests/source/test_no_writes.py`.

## 6. Обработка ошибок

### Backend

* **HTTP-уровень**: единый формат ответа RFC 9457 (`application/problem+json`) через `ApiError` и `problem_response` (`app/core/errors.py`). В ответе обязательны `type`, `title`, `status`, `code` (английский `snake_case`), `trace_id`, человекочитаемые `title`/`detail` на русском.
* **Единообразие исключений**:
  * В новых роутерах вместо `HTTPException` использовать `ApiError`.
  * В сервисном и доменном слое допускаются явные доменные исключения (наследники `ApiError` или типизированные ошибки уровня сервиса), которые на границе API однозначно маппятся в `ApiError` с корректным HTTP-кодом (`400`, `404`, `409`, `422`, `503`), чтобы ошибки валидации не превращались в `500`.
  * Инфраструктурные ошибки (недоступная БД/источник без fallback) не подавляются молча и пробрасываются до общего обработчика.

### Frontend

* API-клиент централизованно разбирает `application/problem+json`, отображает пользователю русское сообщение (`detail` / `title`) и при сбоях 5xx сохраняет/показывает `trace_id` для обращения в поддержку.

## 8. Git: ветки, коммиты и PR

### Именование веток

* Шаблон:
  ```text
  feature/T{номер}/T{номер}.{подзадача}-{2-6-слов-описания}
  ```
* Примеры:
  * `feature/T5/T5.1-dictionaries-cache`
  * `feature/T2/T2.3-tandem-schedule-reader`
  * `feature/T1/T1.0-coding-standards`

### Сообщения коммитов

* Язык описания — **русский**.
* Рекомендуемый формат: `<type>(T<N.M>): <краткое описание>` (допустимо и `T<N.M>: <описание>`):
  * `feat(T5.3): добавить выдачу шкал оценивания`
  * `fix(T1.4): исправить чтение уровня логирования из настроек`
  * `docs(T1.0): добавить стандарты оформления кода`
* Основные типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `ci`.

### Pull Request и проверка перед пушем

* Один PR — одна задача/подзадача (ориентир размера — до ~400 строк diff).
* Перед пушем обязательно локально прогнать:
  ```bash
  cd backend
  ruff check app tests
  ruff format --check app tests
  mypy app
  pytest -q
  ```
* Для frontend (Этап 2) перед пушем обязательны lint, проверка типов TypeScript, тесты и сборка.
